# Independent review: photo editor stickers

**Verdict: Request/spec is mostly implemented, but review evidence is incomplete.** I found no definite defect in the sticker rendering or API validation path by source inspection. I cannot sign off the responsive/capture requirements because the cited capture directory does not exist in this checkout, and the implementation tests do not catch several incorrect behaviors promised by the criteria.

## Request, sentence by sentence

- “Editor de fotos ... texto, efeitos, molduras ou stickers.” The editor card now advertises stickers and the existing text/effect/frame capabilities remain present. The live app at `http://127.0.0.1:8798/` opened the editor controls in PT-BR, including sticker, position, size, and color. The submitted request's simple-local choice is respected by the implementation: sticker drawing is in Pillow and no remote asset path was added.
- “Ferramentas de edição simples...” The UI adds four bounded selects; there is no freeform editing, extra upload, or additional sticker layer. This matches the deferred built-in sticker scope.
- “... deferred stickers to a separate stage. This stage adds the deferred built-in stickers...” The new stage adds six built-in choices (`heart`, `star`, `sun`, `check`, `arrow`, `speech`) and defaults to `none` in the form and API. Existing option defaults are applied in `main.py`.

## Criteria and test strength

1. **Localized controls/default none — implemented; test is partial.** `index.html` has the four controls and `app.js` has PT-BR and English strings. The live app exposes the PT-BR controls and selects `Sem sticker` by default. `test_editor_card_and_controls_are_active_and_bilingual` checks IDs and only some translations; it does not assert all four fields' localized labels/options or that `none` is the default.
2. **Local draw at anchor/size/color, layer order, oriented dimensions — implementation appears correct; tests are not discriminating enough.** `process_image` applies EXIF transpose before `_apply_editor`; `_apply_editor` calls frame, sticker, then text. `test_editor_draws_each_builtin_sticker_at_selected_position` checks that each shape changes pixels in a top-right region and not bottom-left, but runs only one position, one size, and one color without checking pixel color or relative size. `test_editor_combines_filter_frame_sticker_and_text_in_layer_order` checks some overlay and overlap behavior, but its assertions could pass without detecting a wrong frame/sticker ordering. Existing EXIF test is for text only, so it would not catch sticker positioning against un-oriented dimensions. No single targeted test would fail for every possible violation of this combined rule.
3. **Invalid sticker options return 422 before job creation — implemented and meaningfully tested.** `test_editor_rejects_invalid_options_before_job` parameterizes invalid sticker type, position, size, and color, asserts `422 invalid_options`, and asserts the jobs table remains empty. It would fail if any of these validation cases created a job or returned a different response.
4. **`none` pixel equivalence — implementation appears correct; no test.** `_apply_editor_sticker` returns before drawing for `none`, leaving the same frame/text path. No test compares exact output pixels for omitted sticker settings versus explicit `sticker: none`; therefore a regression in defaults or `none` handling could pass.
5. **360 px no horizontal overflow — not verified.** CSS uses wrapping (`.operation-options`) and has a `max-width: 360px` breakpoint, but no test asserts document scroll width at a 360 px viewport. The running browser was inspected at its available default viewport; there are no capture files in `.specs/features/image-editor-stickers/captures/` (the directory is absent), so I could not compare capture states or set viewport dimensions from those captures.
6. **Download formats and failed-job cleanup — existing flow retained; partial coverage.** `test_editor_returns_selected_output_format` tests PNG/JPEG/WebP downloads but submits only `filter: invert`, not a sticker edit. `test_editor_worker_failure_has_no_downloadable_partial_file` checks failed status, rejected download, and no output files, but fails immediately via a monkeypatched `process_image`; it does not simulate failure after a partial file has been written. These tests cover the common path and a failure path but not all requested sticker-specific/partial-write conditions.

## Screen/capture review

I opened the running app and selected the photo editor without uploading a file or submitting a job, so the running app's data was not changed. Its PT-BR editor displayed the sticker controls, six choices, and `Sem sticker` default. The stated capture directory is absent from the repository, so there were no capture sizes or states available for the requested comparison. The live browser surface was at its default viewport; 360 px overflow is therefore unresolved.

## Findings to address

1. **P1 — No verified 360 px layout/capture comparison.** The criterion explicitly requires no horizontal page overflow at 360 px. Add or restore the cited captures, inspect the app at their dimensions, and check `document.documentElement.scrollWidth <= document.documentElement.clientWidth` at 360 px. Evidence: `.specs/features/image-editor-stickers/captures/` is missing and `tests/test_image_editor.py` has no viewport/overflow assertion.
2. **P2 — Pixel-equivalence/default behavior is not guarded.** Add a test that compares image bytes/pixels for otherwise identical legacy settings and explicit `sticker: none`, and assert default form value is `none`. Evidence: `test_editor_rejects_invalid_options_before_job` only checks invalid options; no test asserts equivalence.
3. **P2 — Placement, size, color, orientation coverage is too narrow.** Current renderer tests detect a changed area for all six shapes only at top-right/large/yellow. Add cases that discriminate each of the nine anchors, all sizes, chosen palette color, and sticker position after EXIF orientation. Evidence: `test_editor_draws_each_builtin_sticker_at_selected_position` uses only those single settings; EXIF coverage tests text only.
4. **P2 — Output/failure criteria do not exercise sticker output or a partial write.** The format tests submit only a filter edit; the failure test raises before the renderer can create partial output. Add sticker-enabled output-format cases and an injected mid-write failure if the worker flow supports it. Evidence: `test_editor_returns_selected_output_format` and `test_editor_worker_failure_has_no_downloadable_partial_file`.

## Author fix pass

The author added tests that compare legacy default pixels with explicit `sticker: none`; verify all nine sticker anchors, all three sizes, a selected palette color, and placement after EXIF orientation; submit a sticker-enabled job for each PNG/JPEG/WebP format; and simulate an exception after writing a partial output to confirm worker cleanup. The form now explicitly selects `none`, and the UI test asserts all four sticker controls are localized in both languages.

The review's 360 px visual check could not be repeated because the available in-app browser did not change viewport size through browser zoom. The earlier independent `.specs/features/image-editor/review.md` reviewed the same S2 sticker controls in the live app at 360 px and reported no horizontal page overflow; this stage restores that same UI and renderer from the reviewed commit, plus explicit selection of the existing default. No feature-specific capture files are present, so there is no captured state to compare.

Verification after the fix pass: `uv run pytest -q`, `uv run ruff check src/i_love_open_converter tests`, `node --check src/i_love_open_converter/static/js/app.js`, and `git diff --check` all passed.
